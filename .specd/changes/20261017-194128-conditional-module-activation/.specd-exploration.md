Architecture REQ-006 already requires every reusable module under `modules/` to
be optional and disabled by default. Availability must not select functionality;
disabled functionality must not require its dependencies; enabled functionality
must fail if required dependencies are absent, rather than silently disappear;
independent functionality must remain usable. This is completion of an existing
contract, not a need to invent that requirement again.

The architecture system contract already states:

- `modules/` owns reusable interfaces and their behavior; `config/` consumes
  interfaces to express repository policy; hosts/profiles select behavior.
- Enablement can use an existing boolean or an explicitly supplied value. It
  does not require one new enable boolean for every source file.
- Collection modules and fragments use their owning feature's selection.
- Imports must remain independent of evaluated config, account identity, and
  enablement. Conditional inclusion means conditional application of behavior,
  not dynamic `imports`.
- Enabled behavior retains dependency obligations and ordinary Nix diagnostics.
- Deferred `hm` declarations are valid inputs while the primary home is off.
  Their presence alone does not violate module optionality; don't wrap all HM
  declarations solely to check HM availability.

The architecture validation artifact explicitly says its existing optionality
coverage is limited to user/HM and their consumers, and other module families
need separate validation work. Design should fill that gap.

## Partially conditional modules requiring attention

- `modules/services/gerrit/default.nix:35`: `services.gerrit.enable` is assigned
  `config.hardware.isVps` as an ordinary definition in the reusable layer.
  Plugins, OAuth settings, canonical URL (which reads required
  `services.vps.domain`) and `systemd.services.gerrit` preStart/LoadCredential
  are defined unconditionally. Only firewall ports are explicitly guarded by
  service enablement. Guard service-owned additions by the final service flag;
  review moving VPS-to-Gerrit selection to config and normal override behavior.
  Avoid an enable guard that reads a flag it also defines and creates recursion.
  A disabled service should not leave this module's systemd unit contributions.
- `modules/hardware/hdparm/default.nix:33`: `mkDrives` maps every configured
  drive. Every drive gets a service and a timer definition; only the timer's
  `enable` follows `standby.enable`. Service script and timerConfig read required
  `standby.timeout` even for disabled entries. Empty drives defaults are safe,
  but a disabled populated entry needs to work without timeout or hdparm deps.
  Check mixed enabled/disabled entries independently. The timer attribute
  `Unite` at line 72 looks misspelled; noted only, not validated as a runtime bug.
- `modules/applications/misc/gaming/default.nix:9`: Steam enable tracks
  `environment.gaming.enable` (default false), and kernelModules is guarded,
  but remotePlay/dedicatedServer/localNetworkGameTransfers firewall settings and
  extest.enable=true are written unconditionally. Determine actual upstream
  enablement effects before claiming live firewall leakage. Keep gaming owned

- `modules/applications/networking/default.nix:22`: browser NSS activation is

## Design questions and suggested validation direction

No implementation sequence or precise public interface was finalized. Design
should first decide ownership/selection for each remaining behavior, then write
its normative contract and technical checks before an executable plan.

Resolve:

1. Which currently unconditional policy-only files move to config, and which
   gain reusable interfaces? Name options deliberately, without one-per-file
   boilerplate or a single global switch that couples independent capabilities.
2. Which selections are legitimate existing owner flags/collections, and which
   need a separate opt-out (browser integration, LUKS helper customization,
   format defaults, optional programmer hardware)?
3. Which repository hosts/profiles intentionally need each newly selectable
   feature? Existing installation alone is not evidence of purpose. Avoid
   selecting programmer hardware or KL trust on every host just to preserve an
   accidental unconditional default. Report intended migration differences.
4. How to keep Gerrit and nginx policy overrideable using final service/owner
   selection without recursive enablement or ordinary-definition conflicts?
5. How to coordinate architecture deltas with project-aware-nixos-tests, whose
   test assembly changes are not implemented yet? Establish archive/preview
   order; don't require that unfinished infrastructure just to test this change
   if existing evaluation fixtures suffice.

Suggested evidence (not tests executed during discovery):

- Import reusable collection with required external option interfaces available
  but policy absent; inspect feature-owned services, packages, activation,
  certificates, udev, files and image customization when nothing is selected.
- Exercise explicit enable and disable, partially configured disabled entries,
  unrelated capabilities and missing unused dependencies. Include hdparm disabled
  entries without timeout, mixed drives, Gerrit off without VPS domain, and
  certificates/programmer/keyutils/power effects.
- Force relevant settings or toplevel/activation rather than an unrelated bool;
  for enabled missing-dependency failures assert the intended diagnostic.
- Preserve account-only/no-login/HM-on/HM-off matrix and declaration laziness.
- Compare intended active-host settings and validation-only toplevels; private
  substitutes stay under tests/modules/stubs/private-values and only enter
  nixosValidationConfigurations. Do not change deployable hosts to hide missing
  secrets, build unsupported generic targets, or expand inactive-host support.
- Inspect generated format settings separately from expensive image builds;
  whether any real image build is necessary remains a design choice.
