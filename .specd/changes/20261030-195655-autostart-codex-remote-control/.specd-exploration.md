## Compatibility discovery

The original cloud CLI was newer than the repository's locked package. The
repository's Codex package was built and inspected directly; it supported
`remote-control start` / `stop`, managed app-server daemon commands, Unix
listeners, and the hidden foreground app-server `--remote-control` flag.

Managed daemon bootstrap assumes a standalone executable installation and an
updater. The chosen NixOS integration instead supervises foreground
`codex app-server --remote-control --listen unix://` in a system service.
The standard socket is
`$CODEX_HOME/app-server-control/app-server-control.sock`.
An explicit socket path is supplied to clients through `--remote unix://PATH`;
no dedicated socket environment variable was found in the selected Codex source.

Upstream app-server protocol supports `thread/start`, `thread/resume`, and
`turn/start` without requiring a local interactive client. This resolved the
user's startup criterion in favour of boot startup before login and survival
after logout. Authentication recovery and duplicate-daemon policy were deferred.

No ready Codex NixOS service module was found in the pinned nixpkgs or the
unstable version inspected during discovery. Home Manager's Codex module did
not supply the required daemon service.

## Reviewed design direction

Use a reusable `services.codex` module independent of `hardware.development`
and the repository's primary-user options. It installs its selected package
when enabled, runs a systemd system service under an existing account, and
exposes package, user, home, Codex home, socket path, and remote-control options.
Host policy separately supplies primary-user values and enables the service
on development hosts. No public listener or firewall port is added.

The user rejected the initial design for merely restating requirements; the
revised design describes systemd, options, process environment, and connection
semantics. Concrete implementation paths belong in the plan. Durable design
does not pin a Codex version. Required Tool Sources states a general nixpkgs
rule and a separate SpecD exception. Enabling Codex installs its selected
package in `environment.systemPackages`.

The user reviewed artifacts one at a time, approved the revised design and
plan, and authorised implementation. Artifacts are written in English.
Structural SpecD validation does not establish semantic correctness. Discussion
of scenario placement in requirements versus verify, and stronger artifact

## Implementation and review amendments

- Remove Codex from `environment.developmentPackages`: the enabled module owns
  installation; other development packages, including SpecD, remain unchanged.
- Keep evaluation tests in `tests/modules/codex/default.nix` and the VM test in
  `tests/modules/codex/vm.nix`.
- In host policy, use ordinary option assignments, not `mkDefault`. Explicit
  disabling against that policy therefore uses `mkForce` in tests.
- Make `services.codex.user` mandatory, with no empty-string default. Resolve
  the account directly, inherit home directly, and validate user/home settings.
- Use `lib.getExe` for the configured package and NixOS's
  `utils.escapeSystemdExecArgs` for systemd argument escaping, including `%`/`$`.
- Ensure the user-owned Codex home exists before startup: an explicit missing
  `CODEX_HOME` caused the selected executable to exit during discovery.
- Include `/run/current-system/sw` in service PATH for host development commands.
  Similar upstream uses were found in incus-agent and amazon-ssm-agent.
- The user requested simple flake-based test invocation. Current code exposes
  `nix build .#tests.codex`, combining evaluation and VM derivations; standalone
  impure test commands were removed during review.
- Test infrastructure that preloads all repository modules into future tests
  is a separate task. The user assigned it to another agent and told this agent
