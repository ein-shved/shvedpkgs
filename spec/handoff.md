# Handoff

Проект начинает переходить к SDD-процессу. Артефакты спецификаций должны быть на
английском. Общение с пользователем ведется на русском.

## Current working state

На текущем этапе предполагается, что спецификация на весь проект уже существует
в достаточной для работы форме. Текущая задача не состоит в создании общей
спецификации с нуля; она состоит в том, чтобы провести конкретное изменение
через SDD-процесс.

Активная задача: добавить пакет `codex` для всех development hosts. Для этой
задачи уже заведены SDD-артефакты в `spec/requirements.md` и `spec/system.md`;
implementation plan оформлен в `spec/plan.md`; implementation tasks уже
сформулированы в `spec/task.md`. Дальнейшая работа должна сохранять разделение
между requirements, specification, implementation plan и task queue, описанное
ниже.

В проекте уже есть ADR в `spec/adr/`. Будущая работа должна учитывать принятые
архитектурные решения; позже этот файл планируется преобразовать в базовую
инструкцию для агентов.

## spec/context.md

Назначение: описывает текущий контекст проекта и помогает агенту быстро
сориентироваться в репозитории.

Содержит:

- текущую структуру проекта;
- entry points;
- активные и неактивные хосты;
- важные директории и слои;
- известные private/external boundaries;
- текущие наблюдения о состоянии проекта.

context.md не является нормативным источником. Это inventory/context document:
“что сейчас известно о системе и репозитории”. Он может содержать неполные
наблюдения, исторические пометки и рабочие гипотезы. Его нужно использовать как
карту местности, но не как источник требований или гарантий системы.

Если context.md противоречит requirements.md или spec.md, нормативный приоритет
у requirements.md/spec.md. Если контекст устарел, его нужно обновлять как
справочную информацию.

## spec/requirements.md

Назначение: фиксирует требования к системе с точки зрения потребностей
пользователя/проекта.

Уровень абстракции: высокий, относительно независимый от текущей реализации.
Requirement говорит, что должно быть истинно, но по возможности не привязывает
это к конкретной модели конфигурации, конкретным Nix options, пакетным buckets
или плану реализации.

Должно попадать:

- пользовательская или проектная потребность;
- желаемое observable behavior на уровне пользователя;
- constraints, если они являются частью потребности;
- rationale, если он помогает понять мотивацию;
- acceptance criteria, проверяющие удовлетворение требования.

Не должно попадать:

- план реализации;
- выбор конкретного Nix-модуля или файла;
- “добавить пакет в такой-то список”;
- ADR-уровень решений;
- детали текущей архитектуры, если они не являются частью самой потребности.

Acceptance criteria в requirements:

- проверяют, выполнено ли требование с точки зрения пользователя/проекта;
- не должны диктовать конкретную реализацию;
- могут говорить о наблюдаемом поведении;
- могут задавать условия проверки, например “given valid credentials and network
  connectivity”.

## spec/system.md (system specification)

В текущей рабочей модели речь идет о системной спецификации. В репозитории файл
может называться system.md или быть переименован в spec.md; методологически это
один тип документа: specification.

Назначение: переводит требования в точные, проверяемые правила текущей системы.

Уровень абстракции: ниже requirements, но выше implementation plan.
Specification уже может использовать конкретные понятия и интерфейсы системы:
NixOS host configuration, config.user.name, hardware.development, system
package, package set, command lookup path и т.п.

Должно попадать:

- нормативные системные правила;
- точное соответствие абстрактных понятий requirements конкретным системным
  понятиям;
- observable guarantees;
- system concepts, если они нужны нескольким секциям;
- traceability к требованиям;
- внешние контракты, если они являются частью системной модели и нужны для
  проверки соответствия.

Не должно попадать:

- пошаговый план реализации;
- конкретный patch location, если это не часть системного контракта;
- объяснение “как именно сейчас лучше закодить”;
- ADR-обоснование выбранного решения;
- временные workaround-и, если они не являются контрактом системы.

Связь requirements и specification:

- Requirement говорит: “что нужно”.
- Specification говорит: “какие конкретные правила и гарантии действуют в
  этой системе, в том числе для удовлетворения зафиксированных требований”.
- Specification не должна просто переформулировать requirement более формальным
  языком.
- Specification должна использовать знание текущей системной модели для
  уточнения требования.
- Specification должна иметь traceability к requirement, но не дублировать весь
  текст requirement.

Как определить, requirement это или specification:

- Если утверждение имеет смысл вне текущей реализации и описывает потребность
  пользователя/проекта, это requirement.
- Если утверждение задаёт часть контракта текущей системы и для этого
  использует её конкретные понятия или интерфейсы, это, как правило,
  specification. Само по себе упоминание конкретного системного понятия не
  делает утверждение частью specification: если оно описывает способ достижения
  требуемого состояния, это скорее всего PLAN/implementation.
- Если утверждение отвечает “куда добавить, какой модуль править, какой пакетный
  список использовать”, это уже plan/implementation, не requirement и не
  specification.
- Если утверждение выбирает между архитектурными альтернативами и объясняет
  почему, это ближе к ADR/design decision.

Acceptance criteria:

- В requirements AC проверяют требование на уровне пользователя/проекта.
- В specification вместо AC обычно должны быть точные нормативные правила и
  observable guarantees.
