# Процесс Spec-Driven Development

## 0. Статус документа

### 0.1 Область действия

Этот документ является русским переводом текущего рабочего процесса
Spec-Driven Development (SDD), используемого проектом.

Процесс находится в активной разработке.

Пока открытые изменения явно не приняты, остальная часть документа
определяет текущую рабочую модель.

### 0.2 Английская и русская версии

**Разработка процесса в этом документе не ведётся.** Все изменения
сначала вносятся и принимаются в [английской версии](sdd-process.md).
После принятия изменений английский документ полностью переводится в эту
русскую версию.

Если английская и русская версии расходятся, расхождение считается
дефектом и должно быть заведено и исправлено как баг. До устранения
расхождения **приоритет имеет английский документ**.

### 0.3 Открытые вопросы и TODO

Основные кандидаты на будущий пересмотр:

- **Модель проверки требований.** Сейчас Requirements используют
  критерии приёмки (acceptance criteria, AC). В качестве замены или развития
  рассматривается сценарная модель, близкая по идее к сценариям
  OpenSpec. Формально ограниченный формат сценариев может давать более
  ясные единицы проверки и уменьшать субъективность оценки качества AC.
- **Модель жизненного цикла и статусов артефактов.** Процессу нужна явная
  модель состояний артефактов и переходов между ними: например draft,
  accepted, active, completed, superseded, archived или эквивалентные
  состояния, специфичные для проекта. OpenSpec может дать полезные идеи,
  но любая заимствованная модель должна сохранять описанные здесь зоны
  ответственности артефактов и структуру зависимостей.
- **Интеграция OpenSpec.** OpenSpec рассматривается как инструментарий для SDD
  с участием агентов. Его стандартный workflow не считается определением
  этой методологии. В частности, описанное здесь разделение
  Requirements, System Specification, Plans и других артефактов должно
  сохраняться, пока не принято осознанное решение его изменить.
- **Форматы артефактов и автоматизация workflow.** Структура файлов,
  синтаксис, идентификаторы, состояния жизненного цикла, traceability
  и workflows для агентов могут развиваться по мере внедрения
  инструментов.

### 0.4 Примеры и технологические детали

Примеры могут использовать конкретные технологии, если это делает
границу процесса понятнее. Читателю не должно требоваться предварительное
знание этой технологии, чтобы понять пример. Если технологический термин
важен для примера, нужно дать локально достаточно пояснений, чтобы пример
был самодостаточным.

Предпочтителен самый маленький конкретный пример, который проясняет
правило процесса. Описание технологии не должно разрастаться настолько,
чтобы заслонять иллюстрируемую SDD-идею.

## 1. Назначение и основные принципы

Процесс делает намерения проекта, текущий контракт системы, важные
решения, переходы реализации и исполняемую работу достаточно явными,
чтобы человек или агент могли восстановить картину проекта без
накопленной истории разговоров.

Основные принципы:

1.  **Артефакты репозитория — долговременный контекст процесса.**
    История разговоров и контекст агента являются временными
    вспомогательными средствами.
2.  **У артефактов разные зоны ответственности.** Requirements,
    Specification, ADR, Plans, Tasks, Implementation и любой
    опциональный артефакт Context не должны незаметно присваивать роли
    друг друга.
3.  **Основное направление зависимостей —
    `REQ → SPEC → PLAN → TASKS → IMPLEMENTATION`.** Это модель
    зависимостей, а не необратимый waterfall.
4.  **Discovery может двигаться вверх.** Работа ниже по потоку может
    показать, что ранний артефакт ошибочен, неоднозначен или неполон.
5.  **Исправления распространяются вниз.** Исправляется самый ранний
    затронутый артефакт, затем по порядку пересматриваются зависимые.
6.  **Значимые решения фиксируются явно.** ADR сохраняют важные выборы и
    их мотивацию.
7.  **Завершённая работа заканчивается согласованным и провалидированным
    состоянием.** Валидация устанавливает завершённость, а не
    выполняется церемониально после неё.
8.  **Используется минимально полезная бюрократия.** Артефакт или
    граница нужны только тогда, когда несут отдельную полезную
    информацию.

## 2. Модель процесса

Основной поток зависимостей:

``` text
REQ -> SPEC -> PLAN -> TASKS -> IMPLEMENTATION
       ^       ^
       +-- ADR-+
```

Опциональный ненормативный артефакт Context может помогать discovery и
ориентации, особенно при внедрении SDD в существующий проект. Он не
является частью нормативной цепочки зависимостей.

ADR не является фиксированным этапом pipeline и может возникнуть при
работе на любом уровне.

Стрелки показывают зависимость, а не допустимое направление работы.
Поздняя работа может обнаружить отсутствующую информацию выше:

``` text
REQ -> SPEC -> PLAN -> TASKS -> IMPLEMENTATION
       ^       ^       ^          |
       +-------+-------+----------+
                 discovery
```

В таком случае определяется самый ранний артефакт, корректное содержимое
которого должно было предотвратить проблему. Сначала исправляется он,
затем пересматриваются затронутые нижележащие артефакты.

> **Discovery движется вверх; исправления распространяются вниз.**

### 2.1 Опциональная ветка Discovery/Spike

Когда у проекта есть достаточно известная или предполагаемая потребность
для исследования, но Requirements, системный контракт или значимое
направление дизайна всё ещё слишком неопределены для ответственной
стабилизации Specification, может появиться опциональная ветка
Discovery/Spike:

``` text
REQ -> [DISCOVERY/SPIKE] -> SPEC -> PLAN -> TASKS -> IMPLEMENTATION
```

Discovery/Spike не является обычным обязательным этапом и не является
production-реализацией. Он нужен, чтобы сравнить альтернативы, при
необходимости построить ограниченные прототипы, провалидировать
предположения и получить свидетельства для Requirements, Specification
и ADR.

Discovery/Spike может показать, что Requirements были неполными,
неверными или слишком расплывчатыми. В таком случае используется то же
правило upstream discovery: сначала исправляются Requirements, затем
пересматриваются результаты Discovery/Spike и нижележащие артефакты.

## 3. Модель артефактов

### 3.1 Context

Context — опциональная ненормативная инвентаризация и карта проекта. Он
может описывать структуру репозитория, точки входа, экземпляры системы,
важные слои, внешние/приватные границы, наблюдения о текущей реализации и
полезные исторические сведения.

Context **не** определяет обязательное поведение или гарантии системы.
Он может быть неполным или временно устаревшим. При конфликте приоритет
имеют Requirements и System Specification.

Context наиболее полезен во время внедрения SDD, discovery проекта или
работы с областями, чьи намерения и системный контракт ещё недостаточно
покрыты нормативными артефактами. В идеальном устойчивом состоянии, когда проект
полностью переведён на SDD-процесс, отдельный артефакт Context должен
стать ненужным и может отсутствовать.

Не следует сохранять Context как параллельное описание текущей системы
только ради самодостаточности. Если изменения реализации делают
Context существенно устаревшим, нужно либо обновить всё ещё полезную
ненормативную ориентацию, либо перенести долговременное знание в
правильный артефакт-владелец, либо удалить устаревший материал Context.

### 3.2 Requirements

Requirements описывают потребности, которым должна удовлетворять система
или проект.

Requirement должен быть настолько независим от текущего механизма
реализации и модели конфигурации, насколько это разумно.

Полезный тест:

> Если внутреннюю реализацию или интерфейс конфигурации заменить,
> но исходная потребность останется, будет ли Requirement по-прежнему
> иметь смысл?

Если да, утверждение, скорее всего, является Requirement. Если нет, это
может быть Specification, Plan или деталь реализации.

Этот тест не запрещает конкретные технологии в Requirements. Технология,
формат файла или интерфейс могут принадлежать Requirement, когда они сами
являются частью пользовательской потребности, внешнего контракта или
обязательства совместимости.

Requirements отвечают за потребность или обязательство, область действия,
мотивацию при необходимости и условия определения удовлетворения
потребности.

Они не отвечают за текущие внутренние интерфейсы только потому, что те
реализуют потребность, выбор пакета, модуля или файла, шаги миграции,
архитектурную историю или декомпозицию реализации.

Requirement может использовать доменные понятия, понятные потребителю.
System Specification при необходимости отображает их на текущую модель
системы.

#### 3.2.1 Критерии приёмки и сценарии

Текущий процесс использует **критерии приёмки (acceptance criteria, AC)** для выражения
условий выполнения Requirement.

AC должны проверять Requirement, а не кодировать лишние детали
реализации или системного дизайна.

Эта часть процесса явно находится на пересмотре. Сценарная модель —
главный кандидат на замену или развитие AC. Формально ограниченный
сценарий может давать более ясную единицу ожидаемого поведения и
уменьшать субъективные споры о качестве отдельного AC.

Пока сценарная модель явно не принята, AC остаются текущим механизмом.

### 3.3 System Specification

System Specification — нормативное описание текущего контракта системы.

Она отвечает за:

- стабильные системные понятия и их определения;
- системные интерфейсы и контракты конфигурации;
- нормативное поведение и гарантии;
- связи и инварианты между понятиями;
- значимые внешние контракты;
- отображение абстрактных понятий Requirements на текущую модель системы.

Она отвечает на вопрос:

> **Что должно быть истинно о системе при её текущей модели и
> интерфейсах?**

Полезный тест соответствия:

> Имея реализацию текущей системы, можем ли мы определить,
> соответствует ли она этому утверждению?

Specification — не формальная переформулировка Requirements.
Requirements выражают независимые потребности; Specification формирует
связную модель системы, способную удовлетворить их совокупность.

Например, Requirement может утверждать, что пользователи должны иметь
возможность воспроизвести тот же набор пакетов или зависимостей на другой
машине. Эта потребность может оставаться стабильной, даже если проект
меняет механизм, который её обеспечивает.

Specification описывает текущий системный контракт, удовлетворяющий эту
потребность: например lock-файл, фиксирующий точные версии зависимостей,
сгенерированный список пакетов, который читают потребители, или другой
текущий интерфейс. Если интерфейс меняется, а базовая потребность остаётся,
Requirement может остаться стабильным, пока Specification меняется.

Связь естественно многие-ко-многим:

``` text
REQ-001 --+
REQ-002 --+--> System Concept / Contract A
REQ-003 --+              |
                          +--> Behavior X
REQ-004 -----------------+
```

Одно понятие Specification может участвовать в удовлетворении нескольких
независимых Requirements, а один Requirement может зависеть от
нескольких разделов Specification.

Значимые понятия должны иметь одно место-владельца определения;
остальные разделы ссылаются на него.

Подходящий уровень конкретики в Specification зависит от типа системы и
определяемого контракта. Конкретное значение не становится Specification
автоматически, но и не оказывается автоматически вне Specification.

Нужно спросить, определяет ли утверждение переиспользуемый системный
контракт, интерфейс, инвариант или гарантию, либо выбирает значение для
конкретного экземпляра, развёртывания, политики, набора данных, набора
пакетов или другого применения этого контракта.

Для универсальных систем и фреймворков конкретные значения обычно
принадлежат экземпляру системы, а не системной Specification. Для систем,
цель которых — определить конкретный поставляемый экземпляр, некоторые
значения могут быть частью принятого контракта. В обоих случаях нельзя
позволять доминирующей перспективе проекта неявно решать эту границу.

Specification не отвечает за мотивацию выбора одного значимого дизайна
среди альтернатив, конкретный переход существующей реализации,
пофайловые инструкции и временные механики миграции. Это зоны ADR и
Plans.

### 3.4 Implementation Plan

Plan описывает конкретный переход от текущей реализации к состоянию,
соответствующему Requirements, Specification и принятым решениям.

Plan может содержать связанные артефакты, цель, предположения,
ограничения, наблюдения о текущей реализации, подход к реализации,
минимальный набор изменений, область действия и вне её, порядок
миграции, риски и стратегию валидации.

Он отвечает:

> **Как изменить текущую реализацию так, чтобы она соответствовала
> согласованному системному контракту?**

Plans могут называть конкретные файлы, модули, пакеты, параметры
конфигурации, команды и шаги миграции.

Plan не должен молча вводить новое нормативное поведение. Отсутствующее
понятие, интерфейс или гарантия возвращают работу в Specification; новая
потребность — в Requirements; значимый выбор, мотивация которого должна
сохраниться, — на соответствующий уровень и в ADR.

Полезный boundary test:

> Если утверждение должно оставаться истинным после завершения
> перехода, оно не должно жить только в Plan.

Plans могут описывать, как проект достигает целевого состояния, почему
конкретный порядок перехода безопасен и какая валидация докажет
корректность перехода. Долговременное целевое состояние принадлежит
Requirements и Specification.

Стратегия валидации Plan описывает свидетельства корректности перехода,
включая ожидаемые изменения и сохранение поведения, которое не должно
измениться.

Завершённый Plan — прежде всего история перехода. Текущая истина
остаётся в Requirements и Specification.

### 3.5 Tasks

Tasks декомпозируют принятый Plan на независимо завершаемые единицы
работы.

> **задача** — минимальная практически полезная единица работы, способная
> перевести проект из одного согласованного состояния в другое
> согласованное и провалидированное состояние.**

Каждая задача должна оставлять систему в согласованном и
провалидированном состоянии. Валидация является критерием завершения
задачи, а не отдельной задачей для проверки корректности.

Такая задача может включать несколько шагов реализации, если разделение
создаёт невалидное, несогласованное или непровалидированное
промежуточное состояние.

Эти шаги могут быть записаны как чеклист или выполнены отдельными
коммитами, но они не являются независимо завершаемыми проектными
задачами. Такая задача помечается завершённой только тогда, когда вся
последовательность шагов, включая финальную валидацию, достигла одного
согласованного и провалидированного состояния.

Хорошая граница задачи — точка, где работу можно безопасно остановить.

Подготовительные или не изменяющие состояние задачи допустимы, если их
результат самодостаточно завершён и не ухудшает состояние проекта.
Снятие базового снимка перед миграцией — пример.

Такие задачи выводят решения из Plan, а не вводят новые значимые проектные
решения. Обнаруженное отсутствующее решение возвращает работу на
соответствующий вышележащий уровень.

Если работа по реализации коммитится, артефакт исполнения должен быть
одним атомарным самодостаточным коммитом или цепочкой таких коммитов.
Такая задача не обязана равняться одному коммиту.

Repository Tasks не являются временным TODO-листом агента. Агент может
иметь множество временных шагов исполнения внутри одной задачи.

### 3.6 Implementation

Implementation исполняет задачи в коде, конфигурации, тестах,
сгенерированных артефактах и других материалах проекта.

Локальные решения, не меняющие согласованную системную модель или
значимый дизайн, могут приниматься во время реализации.

Implementation не должна скрывать upstream discovery:

- новая потребность → Requirements;
- отсутствующее системное понятие или контракт → Specification;
- значимый выбор → владеющий слой и при необходимости ADR;
- неверный подход к переходу → Plan;
- небезопасная граница работы → Tasks.

Implementation завершена только после выполнения критериев завершения
задачи, включая валидацию.

## 4. Architecture Decision Records

### 4.1 Роль

Architecture Decision Record (ADR) сохраняет значимое решение, его
контекст, существенные альтернативы и мотивацию выбранного направления.

Он отвечает:

> **Почему был сделан этот значимый выбор?**

ADR — историческое свидетельство решения, а не основной источник текущей
истины о системе.

### 4.2 Когда появляется ADR

ADR **не является этапом pipeline**.

Он может возникнуть при формировании Requirements, Specification или
Plan, а также во время Task/Implementation, если discovery выявляет
ранее не принятое значимое решение.

В последнем случае решение не прячется в коде: работа возвращается на
соответствующий уровень дизайна, решение фиксируется, нижележащая работа при
необходимости обновляется.

Не каждый технический выбор требует ADR. ADR нужен, когда мотивацию
имеет смысл сохранять независимо.

### 4.3 ADR vs Specification vs Plan

- **Specification:** что истинно о системе.
- **ADR:** почему был сделан значимый выбор.
- **Plan:** как выполняется конкретный переход реализации.

ADR может привести к нормативным последствиям в Specification и
конкретным действиям в Plan.

### 4.4 Жизненный цикл и замещение

ADR сохраняют историю. Старые ADR не переписываются так, будто поздние
решения были известны заранее.

Уточнять ADR допустимо, если сохраняются решение и его существенная
мотивация. Поздняя работа может обнаружить конкретный пример,
свидетельство или формулировку, которые лучше объясняют мотивацию, уже
присутствующую в ADR.

Такие правки не должны создавать впечатление, будто позднее знание было
известно на момент решения. Если уточнение существенно меняет решение,
добавляет новую решающую мотивацию или меняет фиксируемый компромисс,
нужно создать поправку или замещающий ADR.

При замене ADR остаётся и явно помечается как superseded, желательно со
ссылкой на замену.

Текущая истина читается из Specification; рассуждения и эволюция — из ADR.

### 4.5 Лёгкое Discovery внутри ADR

Небольшое исследование может оставаться внутри ADR вместо выделения
отдельной ветки Discovery/Spike.

Так стоит делать, когда вопрос достаточно узкий и ADR может зафиксировать
альтернативы, свидетельства и решение, не заслоняя само решение.
Например, ADR может сравнить два небольших примера производительности
или два локализованных API-прототипа перед фиксацией выбранного
направления.

Если работа требует нескольких существенных прототипов, широкой
валидации или может заметно изменить Specification, нужен явный процесс
Discovery/Spike.

## 5. Процесс Discovery и Spike

Discovery/Spike — опциональный процесс для исследования и проектной работы с
высокой неопределённостью. Он используется, когда у проекта есть
достаточно известная или предполагаемая потребность для исследования, но
он ещё не может ответственно стабилизировать Requirements, системный
контракт или значимое направление дизайна.

Он отвечает:

> **Что нужно узнать перед выбором системного контракта или
> направления дизайна?**

Discovery/Spike может определять варианты подходов, представительные
случаи, область прототипирования, критерии валидации, ожидаемые
свидетельства и явные условия остановки.

Он может производить:

- исследованные альтернативы;
- результаты валидации;
- конкретные выводы и отвергнутые предположения;
- риски и открытые вопросы;
- код прототипов;
- рекомендацию для Specification и ADR.

Discovery/Spike сам по себе **не** определяет нормативное поведение.
Код прототипа не является production-реализацией только потому, что
он существует. Если код прототипа переиспользуется, он должен быть
принят через обычный поток Specification, Plan, Tasks и Implementation.

Завершение Discovery/Spike означает, что согласованные вопросы получили
достаточные ответы для продолжения. Результат должен попасть в ADR, если
выбрано значимое направление, и в Specification, если стал понятен
текущий системный контракт.

Если Discovery/Spike показывает, что базовая потребность отсутствовала, была
неполной или неверной, сначала исправляются Requirements, и только затем
его результаты используются для определения Specification или
нижележащей работы.

## 6. Прямой поток

### 6.1 Optional Context → Requirements

Когда Context присутствует, он помогает сориентироваться и даёт
фактический материал.
Существующее поведение не становится Requirement только потому, что оно
существует.

Requirements происходят из реальных потребностей проекта или
пользователя.

### 6.2 Requirements → Optional Discovery/Spike

Когда Requirements или предполагаемые потребности определяют область
работы, но остаются правдоподобными несколько конкурирующих системных
контрактов или направлений дизайна, перед написанием нормативной
Specification используется Discovery/Spike.

Если неопределённость узкая, её можно обработать внутри ADR. Если она
широкая, дорогая или может изменить Specification, нужен явный процесс
Discovery/Spike.

### 6.3 Requirements и Discovery → Specification

Specification превращает независимые потребности в связный контракт
текущей системы: выделяет общие понятия, выполняет отображение
терминологии, определяет интерфейсы, инварианты и поведение, избегает
дублирования общего дизайна и выносит неоднозначность наружу.

Значимый выбор при формировании модели может породить ADR.

### 6.4 Specification → Plan

Planning сравнивает нормативную цель с текущей реализацией и определяет
изменения, сохраняемое поведение, затронутые области реализации,
предположения, риски и способ доказательства корректности.

Если Specification недостаточно описывает целевой результат, сначала
исправляется Specification.

### 6.5 Plan → Tasks

Plan декомпозируется по безопасным границам исполнения.

Гранулярность определяется связными провалидированными состояниями, а не
количеством файлов, строк или желанием превратить каждое действие в
чекбокс.

Если две задачи не могут независимо закончиться в согласованном и
провалидированном состоянии, скорее всего, это шаги одной задачи.

### 6.6 Tasks → Implementation

Нормальный цикл:

``` text
implement
   |
   v
validate
   |-- failure -> исправить внутри открытой задачи -> validate again
   +-- success -> Task complete
```

Падение валидации корректности не создаёт отдельную задачу для
валидации, пока задача реализации открыта.

### 6.7 Completion и Optional Context

Нормативные артефакты должны описывать предполагаемую систему ещё до
завершения реализации.

Если ненормативный Context существует, его нельзя оставлять вводящим в
заблуждение. Нужно обновить всё ещё полезную ориентацию, перенести
долговременное знание в правильный артефакт-владелец или удалить
устаревший материал Context.

Завершённые Plans и Tasks остаются историей перехода, а не альтернативной
документацией текущей системы.

## 7. Обратный поток и Upstream Discovery

Поздняя работа часто выявляет информацию, которую нельзя было уверенно
знать раньше. Это нормально.

Основное правило:

> **Find the first bad artifact. / Найди первый неправильный артефакт.**

Это самый ранний слой, который неверен, неоднозначен или неполон
относительно новой истины.

Примеры:

``` text
Planning обнаруживает отсутствующий системный контракт
-> исправить SPEC
-> пересмотреть PLAN
-> пересмотреть TASKS
```

``` text
Implementation обнаруживает значимое непринятое проектное решение
-> обновить PLAN и/или создать ADR
-> пересмотреть TASKS
-> продолжить implementation
```

``` text
Implementation обнаруживает ранее неизвестную потребность
-> обновить REQ
-> обновить SPEC
-> обновить PLAN
-> обновить TASKS
-> implementation
```

Не нужно чинить нижележащий артефакт только потому, что именно там
проблема стала видимой.

После исправления самого раннего артефакта последствия распространяются
вниз. Нижележащий артефакт может остаться без изменений, если проверка
подтверждает его корректность.

## 8. Обработка дефектов и багов

### 8.1 Классификация

Дефект может быть:

- **Requirement defect** — потребность, область действия или условие
  удовлетворения неверны/неполны;
- **Specification defect** — системный контракт или модель неверны,
  неоднозначны или неполны;
- **дефект решения/дизайна** — значимое направление неверно либо
  отсутствуют мотивация или ограничения;
- **Plan defect** — подход к переходу, предположения, область действия
  или стратегия валидации недостаточны;
- **Task defect** — декомпозиция создаёт небезопасную границу или пропускает
  работу;
- **implementation defect** — реализация нарушает корректные
  вышележащие артефакты;
- **validation defect** — валидация не способна обнаружить существенное
  нарушение.

Категории могут пересекаться. Важен самый ранний артефакт, который
должен измениться.

### 8.2 Дефекты во время открытой задачи

Если валидация падает, задача остаётся открытой.

Implementation исправляется и валидация повторяется. Если сбой
выявляет вышележащий дефект, сначала исправляется он, затем изменение
распространяется обратно к задаче.

Не нужно завершать Implementation и создавать отдельную задачу для
валидации корректности.

### 8.3 Дефекты после завершения

Баг может появиться после завершения, коммита, push, развёртывания или
интеграции:

``` text
PLAN -> TASK -> validation OK -> commit/push -> deployment -> bug
```

Завершение означает согласованность и валидацию относительно знаний и
модели валидации того момента, а не непогрешимость артефактов.

Используется то же правило первого неправильного артефакта.

### 8.4 Исправление завершённых артефактов

Исторические артефакты не переписываются молча так, будто новое знание
было известно изначально.

Если исходный подход остаётся корректным, но завершённый Plan имел
неполную валидацию или требует ограниченной коррекции, в него
добавляется явное дополнение/поправка, из которого выводятся новые
задачи.

Дополнение фиксирует:

- что обнаружено;
- какое предположение, деталь реализации или покрытие валидацией
  оказались недостаточными;
- какое исправление требуется;
- какая регрессионная валидация требуется.

Завершённые задачи не переоткрываются только из-за появления новой
информации. Они были завершены по существовавшему тогда определению
готовности. Корректирующая работа представляется явно.

Новый Plan создаётся, когда нужен существенно другой переход или подход
к реализации, а не ограниченная коррекция.

Если поведение отсутствовало в Specification, сначала исправляется
Specification. Если отсутствовала базовая потребность — Requirements.

### 8.5 Регрессионная валидация

Исправление бага должно закрыть дефект реализации и, если он есть, пробел
валидации, позволивший дефекту пройти.

Регрессионная валидация демонстрирует новый сценарий сбоя или
эквивалентный инвариант, чтобы тот же класс дефекта стал обнаружимым.

## 9. Модель валидации

Валидация имеет разные роли на разных слоях.

### 9.1 Выполнение Requirement

Сейчас AC определяют свидетельства выполнения Requirement. Рассматривается
сценарная замена или доработка.

### 9.2 Соответствие Specification

Валидация Specification проверяет соответствие реализации нормативному
контракту. Свидетельствами могут быть тесты, оценка, инспекция,
статические проверки, поведение во время выполнения и другие подходящие
механизмы.

### 9.3 Стратегия валидации Plan

Plan определяет, как будет доказана корректность перехода: новое
поведение, отсутствие нежелательного поведения, сохранение
незатронутого, безопасность миграции и предположения.

Для перехода, сохраняющего поведение, стоит использовать сильные
свидетельства эквивалентности, если они дёшевы и их смысл очевиден.
Например, воспроизводимая система сборки должна производить одинаковый
вывод для одних и тех же входов, поэтому иногда можно сравнить хэши
вывода или другие идентификаторы сборки до и после структурной миграции.
Это свидетельство, специфичное для проекта, а не универсальное требование
SDD.

### 9.4 Валидация завершения задачи

Валидация является частью определения готовности задачи. Такая задача не завершена,
пока требуемая валидация корректности ожидает выполнения.

### 9.5 Развёртывание и операционная обратная связь

Развёртывание и эксплуатация дают дополнительные свидетельства и могут
обнаружить случаи, пропущенные прежней валидацией.

Это не делает развёртывание автоматически обязательным формальным этапом
валидации. Обнаруженный пробел классифицируется, и обновляется самый
ранний артефакт, который должен содержать новое знание.

> **Валидация является частью установления согласованного состояния, а
> не церемониальной фазой после реализации.**

## 10. Эволюция и история артефактов

Разные артефакты имеют разный срок жизни:

- **Requirements и Specification:** живые нормативные артефакты текущих
  потребностей и системного контракта.
- **ADR:** исторические артефакты решений; замещённые ADR остаются
  историей.
- **Plans:** артефакты конкретного перехода реализации.
- **Tasks:** очередь работы и история исполнения; не текущая
  Specification.
- **Context:** опциональная ненормативная инвентаризация текущего состояния,
  полезный во время discovery или внедрения SDD и удаляемый, когда он
  больше не нужен.

Такое разделение не даёт Plans, Tasks, старым ADR и заметкам реализации
стать конкурирующими источниками текущей истины.

## 11. Traceability

Traceability показывает связи без искусственного отображения
один-к-одному:

``` text
REQ --+
REQ --+--> SPEC concepts/contracts --> PLAN --> TASKS --> commits
REQ --+             ^
                     |
                    ADR
```

Допустимы:

- один Requirement → несколько разделов Specification;
- несколько Requirements → одно общее понятие Specification;
- один Plan → изменения из нескольких разделов Specification/ADRs;
- одна задача → несколько тесно связанных действий Plan, если разделение
  создаёт невалидное промежуточное состояние;
- одна задача → несколько атомарных коммитов.

Артефакты организуются по зоне ответственности, **а не ради
принудительного соответствия один-к-одному между слоями**.

Traceability должна позволять проследить причинность, но не
превращаться в бюрократию, дублирующую содержимое артефактов.

## 12. Работа с агентами и инструменты

### 12.1 Состояние репозитория как контекст агента

Агенты должны получать намерения проекта и состояние процесса прежде
всего из артефактов репозитория.

Здоровый процесс позволяет новому агенту продолжить работу без большой
передачи контекста, дублирующей знания о репозитории.

При установленных соглашениях запросы могут быть короткими:

``` text
Create a Plan for REQ-001.
```

Качество должно происходить из артефактов и правил процесса, а не месяцев
истории разговоров.

### 12.2 Неоднозначность и Discovery

Агенты не должны молча выдумывать отображения или решения для закрытия
вышележащих пробелов. Существенная неоднозначность выносится наружу и
разрешается на владеющем слое.

### 12.3 Repository Tasks и шаги исполнения агента

Repository Tasks — безопасные для интеграции единицы проектной работы.
Агент может использовать гораздо более мелкий временный TODO-список; это
механика исполнения, а не автоматически проектные Tasks.

### 12.4 Инструменты

Инструменты могут помогать с созданием артефактов и навигацией по ним,
зависимостями и traceability, структурной валидацией, workflows для
изменений и дельт, сборкой контекста агента, жизненным циклом и
архивными операциями.

**Методология определяет семантику и зоны ответственности артефактов;
инструменты реализуют или поддерживают workflow вокруг них.**

OpenSpec сейчас рассматривается в этой роли. Его стандартный workflow не
принят как модель процесса проекта. Интеграция может потребовать адаптации
инструмента или осознанного пересмотра методологии. Такие изменения
сначала вносятся в английский документ согласно разделу 0.

## 13. Практическая шпаргалка

### 13.1 Куда относится эта информация?

| Вопрос                                                         | Основной артефакт    |
|----------------------------------------------------------------|----------------------|
| Зачем это нужно проекту/пользователю?                          | Requirement          |
| Какая потребность или обязательство должны быть удовлетворены? | Requirement          |
| Что гарантирует текущая система?                               | System Specification |
| На какое системное понятие или интерфейс это отображается?     | System Specification |
| Что нужно узнать перед выбором системного контракта?           | Discovery/Spike      |
| Почему принято это значимое проектное решение?                 | ADR                  |
| Как будет изменена текущая реализация?                         | Plan                 |
| Как будет валидироваться переход?                              | Plan                 |
| Какую независимо завершаемую единицу работы выполнить?         | Task                 |
| Какой код или конфигурация реализует изменение?                | Implementation       |
| Какая временная ориентация полезна во время discovery?          | Optional Context     |

### 13.2 Я обнаружил проблему — куда возвращаться?

| Discovery                                                   | Куда вернуться                                                      |
|-------------------------------------------------------------|---------------------------------------------------------------------|
| Базовая потребность неверна или отсутствует                 | Requirement                                                         |
| Требуемое поведение, понятие или интерфейс отсутствует/неверен | Specification                                                     |
| Требуется значимый нерешённый выбор                         | Owning layer + ADR                                                  |
| Переход или стратегия валидации неверны                     | Plan                                                                |
| Работа разбита по небезопасной границе                      | Tasks                                                               |
| Вышележащие артефакты корректны, но код неверен             | Implementation                                                      |
| Завершённое изменение пропустило существенный сценарий сбоя  | Найти первый неправильный артефакт; добавить регрессионную валидацию ниже по потоку |

Если есть сомнение:

> **Какой самый ранний артефакт, содержи он известную мне сейчас истину,
> предотвратил бы эту проблему?**

Сначала исправляется он.
