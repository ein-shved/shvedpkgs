# Validation: Host Deployment

## Test Nodes

The `nixos-cli` case: [running tests](../003-testing-infrastructure/validate.md).

- `deployer` runs `nixos` and also serves as the local target
  for invocations by root and a regular user with `NOPASSWD` sudo.
- `rootTarget` is a remote target with root SSH access and sudo disabled.
- `sudoTarget` uses an SSH user with `NOPASSWD` sudo and password prompting disabled.
- `passwordTarget` uses an SSH user with password-protected sudo;
  sudo and password prompting are explicitly enabled.

Minimal generations A/B are built outside the guests for each node,
preserving networking, access, and the driver connection. Guests start with A;
B differs by a harmless `/etc/nixos-cli-generation` marker.
On `deployer`, the test also places a regular flake in `/etc/nixos`
with B configurations for `deployer` and `rootTarget`. Its inputs and build
dependencies are available in the local Nix store; evaluation and building
run on `deployer` without internet access, with substituters disabled.
Configurations and credentials belong to the test.

## Automated Checks

The module checks below are implemented as the `nixos-cli-module` case in
`tests/modules/nixos-cli-module.nix`, using `testers.runNixOSTest`
and registered in `tests/default.nix`.

### Check: Configuration Assembly and Module Enablement

- Covers: [Nix integration](system.md#nix-integration).
- Method: In the case, assemble an isolated set of minimal configurations
  through the real `lib.mkExtendableSystems`, then add and modify hosts
  through `extend`. Nix assertions verify that the module receives the final
  set through `extensions.nixosConfigurations` and that `enable` selects
  installation of the configured package. Separately check target publication
  with `remoteAddress` and `enable` disabled on that target, and target absence
  without an address when `enable` is enabled.
- Evidence: The enabled module selects the configured package; the target set
  reflects additions and changes from the extended assembly. Command installation
  and target publication follow their independently configured settings.

### Check: Generated Catalog and Wrapper

- Covers: [Catalog generation](system.md#remote-catalog-generation),
  [package and wrapper](system.md#package-and-wrapper),
  [entry format](system.md#env-and-target-catalog).
- Method: Install the package selected by the module from the test assembly in
  the VM. In a test overlay, replace its `nixos-rebuild` dependency with a
  recorder that captures argv and `NIXOS_CLI_CONFIG`. Invoke the installed
  command, read the JSON at the recorded path, and check values with driver
  assertions. The set includes keys with differing hostnames, a hostname
  conflicting with a key, and two identical hostnames. Check the address,
  user, both `useSudo` values, and the `askSudoPassword` default for both
  values of the target host's `security.sudo.wheelNeedsPassword`.
  Include a case where the invoking host's setting differs and explicit
  `askSudoPassword` overrides in both directions. Set an unrelated
  `NIXOS_CLI_CONFIG` before invocation.
- Evidence: The wrapper uses the file generated by the module in the Nix store;
  the JSON contains the expected targets and settings. Both names pass the same
  settings upstream; keys take precedence over hostnames. When two hostnames
  collide, the result matches one of those targets, and both targets' keys are
  preserved. The recorder captures the expected `--target-host`, `--sudo`,
  or `--ask-sudo-password` according to the target settings.

### Check: Local Name at Startup

- Covers: [Local name](system.md#local-name-at-runtime),
  [CLI](system.md#cli-and-argument-forwarding).
- Method: In the same VM case, check a catalog without the current hostname
  and a variant with an existing remote entry under that name. Invoke the
  command without a name, with the current hostname, and with remote target
  names; check help and the recorder's argv. Repeat the local case with a
  catalog containing no remote targets. Reproduce hostname lookup failure
  in a Rust test: inject a hostname provider returning `io::Error` and check
  the catalog initialization result. These Rust tests run through the regular
  `doCheck` when building the package for the VM.
- Evidence: The added local name appears in help and resolves to local execution
  without `--target-host`; an existing remote entry retains its address and
  settings. The runtime name is not added to JSON.
  A provider error is returned as a catalog initialization error.

### Check: CLI and Catalog

- Covers: [CLI](system.md#cli-and-argument-forwarding),
  [ENV and catalog](system.md#env-and-target-catalog).
- Method: Rust crate tests in `src/cli.rs` and `tests/cli.rs` check target
  selection, name collisions, separators, OS argument order and values,
  help/version, catalog loading through ENV, invalid and missing files,
  and non-UTF8 paths.
- Evidence: Tests pass; parsing preserves the expected target and argv,
  help/version succeed, and catalog loading errors include the path and return code 1.

### Check: Completion

- Covers: [Completion](system.md#completion).
- Method: Two unit tests for the `completion` module, run through
  `cargo test` and the package's regular `doCheck`: the first checks suggestions
  for hosts, the local name, and the utility's own options according to position;
  the second, parameterized for Bash and Zsh, uses a stub upstream adapter
  to check removal of the selected host and boundary `--`, recalculation of
  words and cursor position, and preservation of other arguments and separators.
- Evidence: Assertions confirm the expected candidates and the exact context
  passed to the upstream adapter for both shells.

### Check: Handoff to Upstream

- Covers: [CLI](system.md#cli-and-argument-forwarding),
  [execution](system.md#update-execution).
- Method: `tests/deployment.rs` inside the Rust crate runs the binary
  without the Nix wrapper, with a `nixos-rebuild` process fixture in the test
  `PATH`. Check target and sudo settings from the catalog and precedence of
  explicit arguments. Pass `--target-host`, `--build-host`, separators,
  and opaque OS arguments, including non-UTF8 values.
  The fixture captures PID, argv, ENV, and cwd, reads stdin, writes
  stdout/stderr, and exits with code 0, a nonzero code, or a signal.
  Also check failure to launch a missing upstream executable and the existence
  and contents of `flake.lock` on entry to the fixture and after invocation.
- Evidence: Automated assertions confirm the expected argv and context,
  the same PID, preserved streams, the upstream code/signal, and launch errors;
  the wrapper leaves `flake.lock` unchanged and preserves arguments controlling it.

### Check: Real Update of the Selected VM

- Covers: [Execution](system.md#update-execution),
  [local and remote targets, sudo password](requirements.md#req-001-updating-the-local-or-a-named-remote-host).
- Method: `tests/pkgs/nixos-cli.nix` invokes the Nix wrapper on `deployer`
  with the real `nixos-rebuild` and a test catalog. From an empty directory,
  execute the exact commands `nixos switch`, `nixos deployer switch`,
  `nixos rootTarget switch`, `nixos test`, and `nixos rootTarget test`
  without additional arguments or source-selection variables.
  They use regular `/etc/nixos` discovery, evaluation, building,
  and `nixos-rebuild` re-execution.
  Cases involving a regular user, updates to `sudoTarget` and `passwordTarget`,
  redirection, and failures pass the prepared B through
  `--no-reexec --store-path` for both `switch` and `test`.
  Separately redirect a named command to another target with an explicit
  `--target-host`. For `passwordTarget`, enter the correct password through
  a guest PTY with `pexpect`, then exhaust attempts with an incorrect password
  in an independent invocation; add an SSH access failure.
- Evidence: A successful invocation activates B on the selected target:
  `/run/current-system` and the marker change; other nodes retain A.
  The `/nix/var/nix/profiles/system` profile resolves to B after `switch`
  and retains A after `test`. Access and password failures return a nonzero
  result and preserve every node's active generation. For the exact commands,
  the working directory is empty before and after invocation.
  Driver assertions check these states.
- Notes: Each variant starts with A.
